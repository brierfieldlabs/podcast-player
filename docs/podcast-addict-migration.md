24 November 2026: owner accepted Podcast Player v1.2.4 on the phone and approved importer development. ## Preview implementation

Reuse Settings > Import & export > Podcast Addict backup. Match active subscriptions by exact RSS URL; within a unique shared feed, compare unique exact enclosure URLs and publication timestamps within 24 hours. Pocket Casts stores its own episode UUID, not the original RSS GUID. Duplicate source or destination enclosure URLs and date mismatches are ambiguous. Report both source and target unmatched counts in unique shared feeds, missing and destination-only subscriptions, resume and favourite differences, historical completion evidence and provisional state overwrite counts. The preview now produces in-memory before/after changes as well as the counts. Source-only episodes and feeds still need a separate acquisition/matching step. The preview never uploads titles or personal records. Confirmed subscription and episode imports use the existing Pocket Casts service and sync, not GitHub or CI.

Candidate current-state mapping: `seen_status=1` maps to played even with a residual resume position; `seen_status=0` maps to unplayed when position is zero, or in progress when positive. Null, unknown flags and invalid positions remain unresolved. Historical completion is evidence, not an override of the current flag. The [AntennaPod migration reference](https://github.com/AntennaPod/MigrationScripts) and local aggregate source observations support investigating this mapping, but it still needs representative on-device verification. Preserve source resume values separately in milliseconds, converted to Pocket Casts seconds. No third-party migration code was copied.

## Statistics

Podcast Addict has day/hour/feed aggregates and separate listening history. Pocket Casts StatsManager stores lifetime listening and saved-time totals, not those detailed aggregates. Its server merge adds local and server totals; directly setting totals risks duplicate counting on both devices. The preview now reports source days, wall time, content duration and selected saved-time counters separately (minutes). These are not proposed additions to existing account totals. The current backup has a large discrepancy between wall time and content duration, so do not substitute one for the other or assume that old statistics are uniformly measured. Determine the supported server replacement or local-only preservation approach, including actual wall listening time versus content duration, before importing any stats. Keep unmatched detail in the original backup, not a new service.

## Staged apply source (24 November)

- The preview carries the destination episode UUID, exact feed and enclosure, date, and before/after state, resume position, favourite and latest listening date. Invalid flag/position/favourite or a resume beyond a known destination duration skips the row. Positive source playback dates and the latest listening-history date are considered; absence of source history does not delete target history. The full multi-event history is not representable by the existing last-interaction field.
- The repository apply method validates the reviewed rows against the current database, rejects stale or ambiguous feed/episode identity, rejects active playback or changes to the loaded episode, skips rows already at the desired state, and writes a local before-state JSONL recovery record before a single Room transaction. It updates existing sync timestamps and the history dirty flag; it does not modify dismissal/archive, downloads, playlist or unrelated fields. The snapshot is not a complete database backup or proven server rollback. A caller must coordinate playback, queue and sync and revalidate unique matches before invoking it. Server behaviour for older imported listening dates, fractional positions (wire format is integer seconds), and multi-batch sync remains unverified.

The Settings preview now offers separately confirmed acquisition and episode-apply actions. The OPML stage must be reviewed, then rerun the episode preview after feeds arrive. The existing worker passes URLs to the usual Pocket Casts feed resolution API and disables automatic downloads.

## Connected import workflow (24 November)

1. Open Settings > Import & export > Podcast Addict backup and select a fresh private backup. Read the counts before taking any action.
2. Select Add missing subscriptions and confirm. The existing OPML worker uses a private no-backup file (rather than exceeding WorkManager input limits), rechecks existing subscribed URLs, resolves and subscribes via the normal service without requesting auto-download, then removes the temporary file. Refresh and re-preview once it finishes. Service resolution can still fail or return redirected feeds; missing feeds must be reviewed again.
3. Pause both devices. Disconnect the importing device from Wi-Fi and mobile data and wait for refresh/import to finish. Preview the local backup again and select Review episode changes; the separate Apply episode changes confirmation explicitly approves the displayed overwrite. Loaded or queued episodes with changes are excluded and counted, so no playlist clearing is required. Remove or finish those entries yourself and re-preview if you want to migrate them later.
4. The transaction rechecks current subscription and enclosure uniqueness, episode identity, previous values, duration, loaded/queued state and offline/playback conditions. It saves a private before-state recovery record and marks changed fields dirty using existing sync mechanisms. Reconnect and refresh afterwards, then compare against Podcast Addict and the other device. Do not perform the import on both devices. Actual account apply still requires the owner's explicit confirmation after reviewing the real preview.

The existing history worker previously selected at most 1,000 pending rows and acknowledged every row in the table. It now acknowledges only sent UUID/date/status combinations, preserving unsent or concurrently modified rows, and requests another run after a full successful batch. A targeted worker regression test covers the full-batch case. Source only; Kotlin compilation and server behaviour have not been verified. Server history-clear markers or newer server listening dates may prevent exact restoration of historical dates. The local UI only displays the latest 1,000 episodes and cannot reproduce every historical event; the original backup retains that detail. Episode state sync separately sends up to 2,000 dirty rows per refresh; test multiple refreshes and cross-device state before declaring completion.

The statistics preview remains read-only until a separate save confirmation. No unsupported analytics events, server total adjustment, or local stats reset has been introduced. ## Historical statistics snapshot

The inspected Pocket Casts statistics interface reads account totals and transmits device counters. There is no supported account-wide replacement or historical-event import endpoint in the available client. Do not manufacture analytics events, subtract remote device totals or change server behaviour. The source statistics are available in the existing Statistics screen as a distinctly labelled historical snapshot, saved only after selecting Review import actions > Save Podcast Addict statistics and confirming. Saving again atomically replaces the previous local summary; it does not accumulate values. Live Pocket Casts totals remain separate and continue to sync normally. If network stats fail to load, the saved historical section is still displayed.

The snapshot contains source day count, recorded wall time, content time, episode-day play count (not distinct episodes), speed/silence/intro/outro/forward/ad/muted-chapter time saved and live-stream time. All eleven source aggregate columns were readable and nonnegative in the private reference backup, with no records or values uploaded to GitHub. A missing or incompatible optional statistics table does not prevent subscription/episode preview. The summary is an atomic JSON file in the Android app-private no-backup directory. It contains no feed URLs or episode titles, is not synchronised, and is not a substitute for the original full backup. Save the same statistics snapshot separately on the tablet if desired; do not repeat the episode import on the tablet. Detailed daily/hourly/per-podcast/event history remains in the original backup. Wall and content totals are deliberately reported separately; their discrepancy is not resolved or relabelled as known actual listening time.
